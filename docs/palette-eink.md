# Lunaria E-Ink — Palette Design

> **Navigation**: [palette.md](palette.md) covers the general palette design philosophy shared by all Lunaria palettes. [vscode.md](vscode.md) covers how this palette is applied to VS Code UI chrome.

[Lunaria](https://lunaria.design) is a family of scientifically-designed, moderate-contrast color palettes. The three original palettes (Light, Dark, Eclipse) are algorithmically generated using the **CAM16 color appearance model** and its uniform color space. E-Ink is the fourth palette — a **hand-tuned chromatic palette** designed for reflective e-ink displays, informed by CAM16 physical modeling but manually adjusted for perceptual readability.

## CAM16 Design Principles

From the [lunaria.design](https://lunaria.design) documentation:

1. **7 evenly-spaced hues** on the CAM16 wheel, deliberately **skipping cyan** (the human eye's worst region for hue discrimination — the "pit of despair" between S and M cones)
2. **soft\* colors**: same lightness as `mediumGray` — fungible, devoid of individual psychological associations
3. **vivid\* colors**: unequal lightness with **cool/warm asymmetry** (cool tones darker), carrying cultural associations (red/yellow → error/warning, magenta/blue → links)
4. **hc\* (high-contrast) colors**: "as dark or light as their respective neutral foreground" — designed for visually-impaired readers
5. **termLow\*/termHigh\***: log-luminance linear mapping from classic ANSI 16-color values into Lunaria's luminance range
6. **bg\* colors**: based on the four cardinal **opponent-process hues** (yellow/blue, red/green)

### Documented Deviations

| Principle | Original Value | E-Ink Value | Rationale |
|-----------|---------------|-------------|-----------|
| soft\* lightness | = `mediumGray` (L\*≈56) | L\*≈49–52 | Syntax body sits at the perceptual midpoint between bg and fg on the warmer, lower-contrast background. |

## Target Device Matrix

This palette is designed to serve as a daily-driver theme across three fundamentally different display technologies:

| Device | Panel | Gamut | Contrast | Strategy |
|--------|-------|-------|----------|----------|
| **BOOX Mira Pro** | B&W E-Ink | None (grayscale) | ~15:1 reflective | Relies on the grayscale ramp (deepBlack → brightWhite) + hc\* colors. soft\*/vivid\* collapse to grayscale but their lightness differences provide some differentiation. |
| **M1 MacBook Pro** | mini-LED (XDR) | P3 wide gamut | 1,000,000:1 | High contrast amplifies perceived saturation. The muted palette prevents harshness; colors appear richer than on sRGB without being overwhelming. |
| **LG IPS LCD** | IPS | sRGB | ~1000:1 | Standard reference. Colors render as designed. Dark details may lose clarity due to IPS glow. |

**Key insight**: On the BOOX Mira Pro, `vivid*` and `hc*` heavily overlap in lightness (both L\*≈23–32), making them nearly identical in grayscale. This is acceptable — hc\* + the grayscale ramp remain the primary differentiators on B&W, while vivid\* provides important color distinction on the other two devices.

## CAM16 Analysis & Physical Constraints

### Why This Palette Is Hand-Tuned

The Light, Dark, and Eclipse palettes are fully generated by the CAM16 pipeline in [`lunaria.ipynb`](../lunaria.ipynb). E-Ink was also run through the same pipeline (cells 63–64 in the notebook), under reflective viewing conditions:

| Parameter | Light (emissive) | E-Ink (reflective) |
|-----------|-----------------|-------------------|
| Ambient illuminant | D55 | D55 |
| Simulated illuminant | D50 (incomplete adaptation) | D55 (complete adaptation) |
| Simulated illuminance | 1000 lux | 3000 lux |
| White screen luminance | 250 cd/m² (self-emissive) | ~28 cd/m² (reflected) |
| Panel reflectance | N/A | 44% |

**Key finding**: Under reflective viewing conditions, the sRGB gamut at e-ink's physical luminance range (Y = 0.03–0.40) is **extremely compressed**. At J' = 7–14 (the working range for foreground colors), sRGB cannot produce meaningful cool-hue saturation — all maximally-saturated colors collapse toward warm orange/red. This is the CAM16 model correctly reporting that at these low luminance levels, the human visual system cannot perceive strong chromatic differences.

Additionally, the physical neutral reflectance values produce a contrast ratio of only 3.3:1 (below WCAG AA), whereas a usable VS Code theme needs ≥ 4.5:1.

### Physical Neutral Reference

The CAM16-computed physical neutral grays under D65, 200 lux ambient, 44% panel reflectance:

| Token | Physical HEX | Theme HEX | Notes |
|-------|-------------|-----------|-------|
| black | `#313131` | `#1E1E1E` | Theme is darker for readability |
| darkGray / fg | `#525252` | `#3D3D3D` | Theme exceeds physical contrast |
| mediumGray | `#5E5E5E` | `#787878` | Theme uses wider spacing |
| lightGray | `#6C6C6C` | `#B8B8B8` | Theme simulates brighter paper |
| white / bg | `#AAAAAA` | `#EEEEEE` | Theme simulates brighter paper |

### Practical Decision

The E-Ink palette is **hand-tuned** rather than algorithmically generated. The CAM16 neutral scale serves as a **physical calibration reference**, but foreground and background colors are manually adjusted to:

1. **Exceed physical contrast limits** for WCAG readability (8.6:1 vs physical 3.3:1)
2. **Preserve cool-hue identity** (blue, green, violet) that sRGB physically cannot produce at e-ink luminance levels
3. **Maintain the paper-like aesthetic** while being usable as a daily-driver code editor theme

The CAM16 pipeline validates that the hand-tuned values are reasonable — they lie in the correct direction from the physical baseline, intentionally amplified for emissive displays that *simulate* the e-ink experience.

## Syntax Highlighting Color Strategy

| Scope Category | Token Tier | Rationale |
|---------------|-----------|-----------|
| Comments | `deEmphFg` | Neutral, recedes into background |
| Keywords (control, modifiers) | `softBlue` | Cool, structured, calming |
| Strings | `softGreen` | Traditional green association |
| Types, classes | `softViolet` | Distinct from keywords, elegant |
| Functions, namespaces | `emphFg` / `softYellow` | Prominent but not alarming |
| Parameters | `softMagenta` | Warm, identifiable |
| Return, throw, regexp | `hcRed` | **Maximum contrast** — these demand attention |
| Errors, invalid, deprecated | `vividRed` / `vividYellow` | Cultural warning associations |
| Diff insert/delete/modify | `bgGreen` / `bgRed` / `bgBlue` | Background washes, non-intrusive |

## Tuning the Palette

The E-Ink palette is hand-tuned using a scientific, parameter-driven approach. Design targets are stored in `eink-targets.json` and the palette is regenerated by `eink-tune.py`.

### How to adjust

1. Edit `eink-targets.json` — change L\* targets, chroma scale factors, or anchor hex values.
2. Run `python3 eink-tune.py` — regenerates `lunaria-eink.json` from the targets.
3. Run `python3 eink-tune.py --validate-only` — check if the current palette meets all targets.
4. Rebuild the VSCode theme: `make -C vscode`.

### Key parameters

| Parameter | What it controls |
|-----------|-----------------|
| `anchors.bg.hex` | Background color (warm paper tone) |
| `anchors.fg.hex` | Foreground color (body text) |
| `tiers.soft.L*` | Per-hue lightness targets for syntax highlighting |
| `tiers.vivid.L*` | Per-hue lightness targets for emphasis colors |
| `tiers.vivid.chroma_scale` | Saturation reduction (< 1 = desaturate) |
| `tiers.hc.L*` | Per-hue lightness targets for critical tokens (must stay near fg) |
| `contrast.target_bg_fg` | Acceptable bg-fg contrast ratio range |

### Scientific method

The tuner uses the **OKLCH** perceptually-uniform color space to adjust lightness (L) while preserving hue (h) and chroma (C). L\* targets are specified in the CIE L\*a\*b\* perceptual lightness scale. The script uses binary search to find the exact OKLCH lightness that hits each L\* target, then validates all constraints (contrast, tier gaps, sRGB gamut).
